# Subway Mate

Subway Mate is a phone-friendly, local-first wayfinding demo for Times Square–42 St. Routes are calculated from `shared/times-square.json` and `shared/guidance.js`; local routing does not require a server or network, while elevator inventory refresh, optional voice transcription, and explicitly requested online camera assistance use same-origin server endpoints.

The default route starts at the 42nd Street and Seventh Avenue entrance, so you can type a destination directly. Subway Mate does not determine your indoor location: if you are elsewhere, describe a known sign/landmark or scan a photo and confirm the match before routing. From the default entrance it can route to the uptown/downtown 1/2/3 platforms and the 7 platform. It also has a graph path toward the Broadway plaza shuttle connection, but shuttle platform access is not verified in this map. A verified step-free route is supported from the 43rd Street and Broadway northwest-corner entrance to the uptown N/Q/R/W platform. Select **Step-free route (avoid stairs)** to reveal a button that explicitly confirms you are at elevator EL619 and starts that route; do not use it from another entrance. Other step-free destinations are refused with the available mapped option explained. The station graph has no verified step-free path to the 1/2/3 or 7 platforms. The local map does not yet support downtown N/Q/R/W.

“Brooklyn” is mapped specifically to Atlantic Av–Barclays Center, not to every Brooklyn station. The route goes to the downtown 1/2/3 platform and tells the rider to board only a Brooklyn-bound 2 or 3; it explicitly warns not to board a 1. The official station-complex record identifies Atlantic Av–Barclays Center as complex 617 (GTFS stop ID 235). Service patterns can vary, so riders must check the actual train sign.

If lost along a mapped path, describe a station-file landmark (for example, “I'm lost; I see the green globe. Take me to Queens”) or use **Check a sign photo**. Chat separates the location you report from the destination you ask for, so a mention of “7 train stairs” won't override a request to go to the Bronx. If you give a destination but the location is unclear, it keeps that destination while asking for a better clue; after you identify yourself, it resumes from that location. Its reply identifies where you are and where you want to go, then gives one graph step, a clear place to stop, and asks you to say “I'm there” or tap **I've completed this step**. **Back one step** lets you recover from an accidental confirmation. It does not repeat a “take this train / first” preamble. Generic nearby descriptions are checked conservatively: Broadway alone, 42nd Street without its cross street, turnstiles, and an unnamed shop cannot identify a node. An unknown location prompts for sign direction and train markers, a street corner, or an elevator code instead of returning a generic answer. The local OCR reader starts warming up as soon as you enter the route screen, while you can continue entering a destination. It reduces large camera images to at most 1280 pixels on the longest side and uses sparse-text recognition. The UI shows model-loading and scan progress; an individual OCR job stops after 15 seconds with a retry/retake prompt instead of appearing to hang. The first visit still needs to load the bundled reader files; the production PWA caches them for later offline use.

Photo text is read on-device with the bundled English OCR model, then compared only with station-file sign markers and distinct text cues such as “green globe,” “42 mosaic,” or a mapped shop name—those words/numbers must actually be visible to OCR. It does not recognize objects, colors, or logos. Local OCR never uploads its photo. An optional **Analyze this frame online** action can inspect one compressed still from the live camera after you tap it; that frame is sent to the Subway Mate server and xAI, is not stored by the app, and video is never streamed to the model. It is available only when `XAI_API_KEY` is configured. The online model may be wrong: its result is restricted to exact cues and node IDs in the station file, remains a suggestion, and requires you to confirm that you are physically there before routing changes. Ambiguous or unsupported clues prompt for more information; analysis never advances a route step. Without a configured key or network, local OCR, typed guidance, and graph routing remain available. The app computes a new path only after you confirm a mapped location. Route links include explicit instructions in both directions, so a rider matched at the 7 stairs can be guided back toward the requested 1/2/3 platform. Separate station areas without a verified graph connection remain disconnected rather than guessed. Without a destination, the app remembers that confirmed start while you choose where to go. Destination-only requests use the default 42nd Street/Seventh Avenue entrance; if you are elsewhere, first describe or confirm a mapped start point.

The route database stores visual cues for the 1/2/3 signs, 7 stairs/platform, Broadway plaza/shuttle area, and the EL619/EL230 entrance and platform; route steps show only cues encoded for that map node. The lost-rider screen now lists known clues: the green globe, 1/2/3 roundel with direction, purple 7 bullet/tile, 42 mosaic, the dated Knickerbocker Hotel sign cue near the shuttle area, elevator IDs EL619/EL230, and the two mapped shop names (McDonald's and Baskin-Robbins). Shop matches indicate only their mapped street entrances/plaza; they do not identify an interior platform. Turnstiles, fare gates, ticket machines, unnamed shops, and generic signage are not unique location markers. For these, Subway Mate asks for the nearest line/direction text, street corner, exit, or shop name instead of guessing. The app records publicly described Wikimedia Commons cues with source and license metadata, including the Bronx-bound 7th Avenue passageway, uptown Broadway “42” mosaic, 7/Flushing Line escalator area, and a dated shuttle-area hotel sign. These descriptions are not an exhaustive or surveyed indoor landmark inventory. The supplied YouTube page exposed its title but no captions or video frames here, so no cues are claimed to be extracted from that tour. The optional video preview is not a sign reader; use the separate photo action to select or take a still image. **Try a sample sign** exercises the same local OCR flow without being in New York or using a real station photo. Photo matching is deliberately conservative and covers only direction/line markers and distinct text cues encoded for known nodes in the station file. A shared elevator code such as EL230 or the shared IRT Flushing Line cue remains ambiguous between nodes. Photo matching cannot interpret arbitrary scenes, verify that a sign is current, recognize a rider's exact position, or replace accessible station staff. For an unmatched location, read the nearest sign's direction and train markers or give a street corner/elevator code; the app will not guess. Press **I've completed this step** only after completing the displayed direction, or say “okay, I'm there” to advance exactly one step. Directions are brief; the full itinerary remains on screen.

The visual-cue list now also recognizes “IRT Flushing Line,” an alternate name for the 7 line, but keeps it ambiguous between the 7 stairs area and platform. This wording is supported by a Wikimedia Commons photo caption for an escalator toward the IRT Flushing Line platforms (June 2013, CC BY-SA 3.0); it does not establish present-day escalator operation. The station file cites the MTA's **Subway Entrances and Exits: 2024** dataset (`i9wp-a4ja`) for street-entrance types and coordinates. That inventory is static and is not used to infer indoor connections. Route directions remain local and graph-grounded; the online vision endpoint recognizes only cues from the station file and never generates route instructions. It uses the configured xAI vision model for one still frame only—this is not custom-trained or continuous visual tracking.

During a route, ask **“What sign should I look for?”**, **“Where am I?”**, **“Which way do I go?”**, **“Am I going the right way?”**, **“Which train do I need?”**, or **“I can't find the sign.”** Subway Mate answers from the current graph checkpoint and destination, gives the sign wording/visual cue encoded for the next step, or asks you to pause and describe/photograph a sign when it cannot locate you. It does not claim it can see your live position. At the destination it repeats the platform-specific boarding check; it does not claim the rider boarded the train. The journey card and a “when is the train?” question show the next one or two trains from subwayinfo.nyc, with how old that check is. That feed is not the MTA’s own GTFS feed. A train that arrives before the mapped walk can reach the platform is left off. Elevator answers stay on the periodic MTA inventory, not a live outage feed.

The station file records Times Sq-42 St/Port Authority complex 611 and official line/stop metadata from New York Open Data (`5f5g-n3cz`). The server optionally refreshes the official elevator asset inventory (`94fv-bak7`) through `/api/mta/elevators` and caches it for five minutes. This is periodic inventory, **not a live outage feed**. The stored inventory reports EL619, EL231X, and EL230 as in service, and EL229, EL232, and EL233 as out of service; step-free routing excludes equipment with a non-IFIS status. If the endpoint is unavailable, the app uses its dated offline snapshot and displays a warning. The cited GTFS-Pathways endpoint did not provide data (HTTP 403); the complex dataset identifies services and stations, not indoor corridors. Do not treat those records as a complete station topology.

The current step, train, platform, and step-free status can be asked about in chat or by voice. A clear “okay, I'm there”/“I've completed that step” advances one edge; “okay” alone does not. The full itinerary is visible, while spoken guidance gives only the current next step and reminds the rider to check the line/direction sign before boarding. Browser speech recognition is attempted first. If unsupported, the voice button records only when server transcription is configured with `XAI_API_KEY`; the recording is sent only to the same-origin server for transcription. Without that key or a connection, the app explains the limitation and keeps text input available.

## iMessage through Photon Spectrum

The Express server also starts the optional Photon Spectrum cloud iMessage provider when `SPECTRUM_PROJECT_ID` and `SPECTRUM_PROJECT_SECRET` are set in the local `.env`. The app uses the existing project ID from the provided setup command; obtain the project secret through Photon authentication, never commit it or paste it into chat. After the credentials are set, restart `npm run dev`. If credentials are missing, the web app still runs and the server logs that iMessage is disabled. This integration uses Spectrum's **Stable** `spectrum-ts` SDK and managed cloud iMessage provider; recipients/authorized numbers and line setup are managed in Photon.

The iMessage assistant shares the station graph and deterministic route logic with the website. Text destinations, mapped lost-location clues, step confirmations, route questions, and step-free route limits work in the chat. It gives one graph step at a time. After all route steps are confirmed, send `end`, `thanks`, or `thank you` for “Okay, have a great rest of your day.” Gratitude before arrival does not falsely end the route. It ignores non-message provider events and suppresses duplicate deliveries by Spectrum message ID; it does not send an unsolicited greeting on empty or unrecognized events. It does not emit typing indicators while filtering provider events.

You can attach a JPEG, PNG, or WebP sign photo in iMessage. HEIC/HEIF attachments are not supported; for the demo, use the text-only landmark script below. Supported photos are normalized locally before bundled English OCR (large images are reduced to a 1280-pixel edge). The bot compares recognized text against the same station-file markers and cues as the website. It proposes a mapped location but does not relocate the rider or advance a step until they reply `CONFIRM LOCATION` (or specify a candidate after that phrase). Ambiguous, unsupported, undecodable, oversized, and non-image attachments are rejected with an explanation. Photo content passes through iMessage/Photon and the Subway Mate server, unlike the website's local-only OCR; don't send a photo unless you're comfortable with that processing.

### Photon text demo script

Start a fresh iMessage conversation (or send `Hi`) and use only landmarks you are actually looking at:

| You send | What to expect |
| --- | --- |
| `Hi` | The bot asks where you want to go from Times Square–42 St. |
| `Bronx` | It gives the first graph-based direction from the default 42nd Street and Seventh Avenue entrance. |
| `I'm here` | It advances exactly one step and gives the Uptown/Bronx 1/2/3 direction. |
| `I'm lost` | It asks for the nearest landmark or sign, offers examples, and keeps the Bronx destination. |
| `I'm at the Downtown 1/2/3 sign` | If that is what you see, it identifies this as the wrong direction for the Bronx and gives a mapped route from there. |
| `I'm at the green globe` | If you are physically by the green globe, it recognizes the Uptown 1/2/3 side as the correct direction and reminds you to check the Bronx/Uptown sign. |

You can also answer the lost prompt with `I see a purple 7 bullet`; the bot asks whether you are by the 7 stairs or at the platform because that clue alone is ambiguous. Reply `stairs` or `platform` based on where you are; it keeps the Bronx destination and gives a route from that mapped point. If you cannot identify a mapped landmark, send the exact sign words plus the train number/letter and direction. After each instruction, say `I'm here` only when you have reached that step. This is a text demo, not a reason to walk toward an unfamiliar area; follow station signs and ask staff if the described route doesn't match what you see.

To connect the provided Photon project, run the requested command from any temporary folder and finish the browser device sign-in when prompted:

```bash
npm create spectrum-project@latest bigredhacks -- --projectId 99278541-bf6c-44ab-912a-d9888a3acea5 --providers imessage --yes
```

The scaffold writes `PROJECT_ID` and `PROJECT_SECRET` into its `.env`. Copy those values into the root `.env` as `SPECTRUM_PROJECT_ID` and `SPECTRUM_PROJECT_SECRET` (the project ID is already listed in `.env.example`); keep the secret local. Start the Subway Mate server and verify `/api/health` reports `"imessage":"connected"` or check for `Photon iMessage assistant is connected.` The bot's state is held in memory per conversation and resets when the server restarts. Use the text demo above to test destination selection, step confirmation, wrong-direction recovery, and the lost-landmark prompt. Photo testing accepts JPEG, PNG, or WebP only.

To test photo wayfinding: enter a destination screen and wait until it says **On-device sign reader ready** (the first model load may take a while). Use **Try a sample sign** → **Uptown 1/2/3** to test a positive image without traveling; it should suggest the Uptown platform. Then use **Take a photo** and photograph that sample on another screen or a printout, filling the camera view with the sign and holding steady. The same route should be suggested after OCR finishes. Test **Downtown N/R (should not match)** and **Blank wall (no match)**; neither should suggest a platform. The recognized text is shown so you can see whether camera framing or glare caused the miss. A photo scan never changes the active step.

To test online camera assistance, configure `XAI_API_KEY` in the server environment, start the app, begin any route, enable the camera preview, then tap **Analyze this frame online**. The browser submits one downscaled still—not a video stream—to the Subway Mate server and xAI. The response can suggest only station-file cue matches; it must not change the route or step. Check that a known cue offers a confirmation button, a shared clue such as **IRT Flushing Line** stays ambiguous, and an unmatched scene asks you for readable sign text. Confirm only when you are actually at the suggested place. Without the key or network, camera assistance is unavailable but local OCR and typed routing remain usable. Never send a frame you do not want to share.

For street-location testing, photograph a clear **Baskin-Robbins** storefront/name. That maps only to the Broadway plaza entrance, where the station file lists the shop nearby; it is not evidence that you are already at an Uptown/Downtown platform. From that confirmed entrance, choose a Bronx destination and the route graph continues toward the appropriate 1/2/3 sign. A clear **McDonald's** name maps to the 42nd Street and Seventh Avenue entrance. For the N/Q/R/W route, confirm **EL619 at the northwest corner of 43rd Street and Broadway**, then request Uptown N/Q/R/W and check the platform sign before boarding. 1/2/3 platform signs need direction words and line markers (for example, **UPTOWN / BRONX / 1 2 3**) to distinguish them safely. If a photo reads no text, move closer, reduce glare, and keep the sign level and filling most of the frame.

To test the Brooklyn route away from New York, type **Brooklyn**. The itinerary should lead to the downtown 1/2/3 platform and say to board only a Brooklyn-bound **2 or 3**, never a 1. This is a destination/boarding demo, not a complete route map for Brooklyn.

For a live walk, once at Times Square, photograph actual station signs at each step and compare the detected text/candidate with the sign in view. To test online visual help, enable the camera preview and tap **Analyze this frame online**; review the proposed clue and confirm only if you are physically at that mapped location. The single frame is sent to xAI through the configured Subway Mate server; do not use the feature if you do not want to share the image. These samples and landmark aliases are checks against the local station graph, not proof that a sign, shop, elevator, or route is currently present or open.

## Run

```bash
npm install
npm run dev
```

Open https://localhost:5173 for desktop testing. `npm run dev` starts Vite and the Express server. Routing stays local; the app optionally requests the MTA elevator inventory through the server. If that request fails or you are offline, the dated station-file snapshot remains available and the screen warns that it is not live status.

### Test on a phone

Put the phone and computer on the same Wi-Fi and find the computer's LAN IP (on macOS, check **System Settings → Wi-Fi → Details → TCP/IP**). The default Vite development certificate is for `localhost`; for phone testing, make a short-lived certificate that includes the computer's IP. Replace `10.0.0.42` in the command with that IP:

```bash
openssl req -x509 -newkey rsa:2048 -sha256 -nodes -days 7 \
  -keyout /tmp/subway-mate-key.pem -out /tmp/subway-mate-cert.pem \
  -subj "/CN=10.0.0.42" \
  -addext "subjectAltName=IP:10.0.0.42,DNS:localhost,IP:127.0.0.1"
SUBWAY_MATE_CERT=/tmp/subway-mate-cert.pem \
SUBWAY_MATE_KEY=/tmp/subway-mate-key.pem npm run dev
```

On the phone, open `https://<computer-LAN-IP>:5173` and proceed past the browser's self-signed-certificate warning. Keep the private key in `/tmp`; do not commit it. This certificate is only for local testing. If your LAN IP changes, regenerate it with the new address. If the page does not load, check that both devices are on the same Wi-Fi and that the network allows devices to communicate.

Run the focused station and route checks and build with:

```bash
npm run check
npm run build
```

Typed destinations and route guidance work offline from the bundled station file. Photo text reading uses a locally bundled OCR worker, core, and English model (about 9 MB); the production service worker precaches these same-origin assets so subsequent photo checks work offline after the app has been opened once. Local sign-photo scans stay in page memory and are never sent to the server. Only the separate, explicitly requested online camera action sends one compressed frame to xAI through the same-origin server; `XAI_API_KEY` stays on the server and is never included in the browser bundle. Speech output uses the browser's local speech synthesis; browser speech recognition may require an online service and is optional. Camera access is separately optional. The interface makes no external font/API requests.
